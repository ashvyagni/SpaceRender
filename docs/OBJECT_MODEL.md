# Object model

One schema for every celestial object, so the creator, the inspector, saves, provenance and
the physics engine all speak the same language.

## Taxonomy

`ObjectClass` names *what an object is*. It is independent of how the object is simulated.
Classes marked ✅ can be created and simulated today; the others are defined so data,
saves and UI can refer to them, and are implemented milestone by milestone.

| Group | Classes |
|---|---|
| Stars | ✅ main-sequence star · protostar · brown dwarf · ✅ giant (evolved) · ✅ white dwarf (remnant) · neutron star · pulsar · magnetar |
| Black holes | stellar-mass · intermediate · supermassive |
| Planets | ✅ rocky planet · ✅ ocean world · ✅ ice world · lava world · ✅ gas giant · ✅ ice giant · dwarf planet · rogue planet |
| Satellites | ✅ moon (any planetary class with a parent) · binary planet |
| Small bodies | ✅ asteroid · meteoroid · ✅ comet (nucleus) · centaur · trans-Neptunian object |
| Diffuse | rings · dust · debris field · nebula · molecular cloud |
| Large scale | star cluster · galaxy · dwarf galaxy · quasar / AGN |

Today a planet-like object is stored as a `Body` (`BodyKind` Rocky / Icy / GasGiant /
IceGiant gives its *physical regime* — surface or not, climate model, rendering), and its
`ObjectClass` refines the label and creator presets. Stars are stored as `Star`.

## Physical representation

| Field | Units | Notes |
|---|---|---|
| mass | kg | `gm = G·m` is derived; never stored separately |
| radius | m | collision radius = radius |
| position, velocity | m, m/s | relative to the system frame (N-body) or derived from the orbit (Kepler) |
| orbit | a (m), e, i, Ω, ω, M₀ (rad) | Kepler mode authoritative; N-body mode shows osculating elements |
| rotation period | s (negative = retrograde) | |
| axial tilt | rad | |
| albedo | Bond albedo | |
| atmosphere | bar + volume fractions | N₂, O₂, CO₂, H₂O, CH₄, H₂/He |
| hydrosphere | Earth-ocean equivalents, coverage fractions | |
| magnetic field, geology | relative to Earth | |

Derived (computed, never stored): surface gravity, density, escape velocity, Hill sphere,
Roche limit, equilibrium temperature, insolation, habitability.

Internally everything is SI. Unit conversions live in one place
(`cosmogon_sim::units`) and the UI chooses display units (kg / M⊕ / M♃ / M☉; m / km / R⊕ /
R♃ / R☉ / AU; m/s / km/s; K / °C).

## Provenance — the data truth system

Every scientifically relevant quantity carries a `Quality`:

| Quality | Meaning | Example |
|---|---|---|
| MEASURED | From an observational dataset | Earth's mass; JPL Horizons state vectors |
| DERIVED | Computed from measured values by a documented model | surface gravity from mass and radius |
| ESTIMATED | Model output with no direct measurement | an exoplanet's atmosphere |
| PROCEDURAL | Generated by Cosmogon from a seed | everything in a procedural system |
| USER MODIFIED | Changed by the user in a sandbox | "Jupiter mass × 2" |

Each body has a `Provenance { source, fields }`: `source` names the dataset (with version)
or "Cosmogon procedural generation (seed …)" or "Created by user"; `fields` maps quantity
names to their `Quality`. Quantities not listed inherit the source's default (MEASURED for a
dataset, PROCEDURAL for generated objects). Editing a quantity marks it USER MODIFIED;
quantities recomputed as a consequence (temperature after moving a planet) are DERIVED.
A missing measurement is never filled with an invented exact value: it is ESTIMATED or
PROCEDURAL and labelled as such.

## Editing rules

* All modifications go through `cosmogon_sim::edit::Edit` commands; the UI never writes to
  the model directly. Each edit is validated, applied, journalled, recorded in history and
  propagated (see SANDBOX_VISION.md, event pipeline).
* Editing a system makes it dynamic (N-body), so the change has physical consequences.
* Dependent quantities recompute automatically: changing mass changes gravity, density,
  escape velocity, the body's gravitational pull and its parent's orbit around the
  barycentre. Surface gravity can be *set* with a choice of which quantity to hold fixed
  (mass or radius).
* Physically unusual inputs produce warnings, never refusals (except values that would
  corrupt the simulation: NaN, non-positive mass or radius):
  * density outside 300–25 000 kg/m³ ("unusual" / "exceeds ordinary planetary matter");
  * inside the parent's Roche limit;
  * unbound orbit (specific orbital energy ≥ 0);
  * time step insufficient for an encounter.
* Bodies are never deleted from storage: deletion, merger and destruction set a `removed`
  record (time, cause). References stay valid; undo restores them.

## Blueprints (planned)

A blueprint is a body serialised without position/velocity plus its provenance and
creator metadata, stored per profile; inserting one goes through `Edit::AddBody`.
